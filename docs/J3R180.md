# J3R180 (NXP JCOP4 SECID) — compatibility & operations guide

Status: **all 4 applets working on hardware** (verified 2026-03-20, issue
[#1](https://github.com/Amperstrand/specter-javacard/issues/1)).

This document covers what works, why it almost didn't (transient RAM), how to
install and reinstall the applets, and per-applet quirks. Card-specific keys and
CPLC serials live in the repository `AGENTS.md` and are not duplicated here.

## The card

| Property | Value |
|---|---|
| Chip | NXP P71D321 (SmartMX3), JCOP4 |
| ATR | `3BD518FF8191FE1FC38073C821100A` |
| JavaCard / GP | JavaCard 3.0.4-class API, GlobalPlatform 2.3, SCP02 (i=15/35/55/75) |
| Protocol | T=1 |
| Host-side | Tested with Gemalto PC Twin Reader |

Two J3R180 cards exist on the bench. They **do not share key state**: one is in
factory state (transport keys, key version 0), the other is personalized with
the default demo key set at key version 1. Check `AGENTS.md` ("Identifying
Cards", CPLC serials) before issuing GP commands — a failed SCP02
INITIALIZE UPDATE consumes a retry counter.

## Transient-RAM constraints and the layered-init design

The original code allocated ~1234 bytes of `CLEAR_ON_DESELECT` transient RAM in
the `SecureApplet`/`SecureChannel` constructors (heap 768 B, HMAC-SHA512
internals 192 B, SecureChannel IV/MAC/AES objects ~144 B, PIN HMAC buffer).
The J3R180's `CLEAR_ON_DESELECT` pool is far smaller than that, so LOAD
succeeded but `INSTALL [for install and make selectable]` failed with `6F00`.

Four strategies were tried (see issue #1 for the full saga); the one that works
is **layered / lazy initialization**:

| Layer | What | When it runs |
|---|---|---|
| Constructor | `TransientHeap(384)` (`CLEAR_ON_RESET`), `PinCode`, RNG init | install time only |
| `ensureInitialized()` | `Crypto.initEssential`, `Secp256k1.initCore`, `new SecureChannel(heap)` | first `process()` APDU |
| Per-feature | e.g. HMAC-SHA512 (PBKDF2 / BlindOracle), SecureChannel session keys | first use |

Source-verified today at `src/main/java/toys/SecureApplet.java`
(`ensureInitialized()`, `LENGTH_TRANSIENT_HEAP = 384`).

Practical consequences:

- Install-time transient allocation is minimal; runtime peak heap use is 271 B
  (`encryptMessage`) against a 384 B heap.
- Scratch buffers are `CLEAR_ON_RESET`: after a card power-cycle the first
  secure-channel APDU re-runs the deferred initialization — the **first APDU of
  a session does extra work**; that is expected, not a fault.
- A memory-diagnostic APDU exists (`CLA A0, INS 00` returns persistent +
  transient-free space as three shorts) but only in builds compiled with
  `DEBUG_BUILD = true` (off in production).

Related: on the smaller-transient J3H145, install-time still overflowed with
SCP02 present; PR
[#4](https://github.com/Amperstrand/specter-javacard/pull/4) (rebased as
`pr4-rebase-j3h145`) additionally defers the ~96 B of SecureChannel session-key
objects to the first `openChannel*()` call. Track issue
[#3](https://github.com/Amperstrand/specter-javacard/issues/3).

## Install flow (J3R180)

Prereqs: `pcscd` running, reader attached, `gp.jar` (GlobalPlatformPro, v25.10.20
in repo root), CAP file from CI artifacts or a local UTF-8-locale build.

1. Identify the card and its key state (see `AGENTS.md`):

   ```sh
   java -jar gp.jar -d --info        # CPLC serial -> which card is inserted
   ```

2. Install (example: MemoryCard; use the card's keys — see `AGENTS.md`):

   ```sh
   java -jar gp.jar --key-enc <ENC> --key-mac <MAC> --key-dek <DEK> --key-ver <V> \
       --install build/cap/MemoryCardApplet.cap
   ```

   On the card personalized with default keys this is simply
   `java -jar gp.jar --key 404142434445464748494A4B4C4D4E4F --key-ver 1 --install build/cap/MemoryCardApplet.cap`.

3. Verify:

   ```sh
   java -jar gp.jar --key ... -l    # package + applet must show SELECTABLE
   ```

4. **Reinstalling: delete the package AID first** (JCOP4 rejects INSTALL over an
   existing package with the same AID — this is the #1 cause of confusing
   install failures):

   ```sh
   java -jar gp.jar --key ... --delete B00B5111CB --force
   java -jar gp.jar --key ... --install build/cap/MemoryCardApplet.cap
   ```

Package AIDs (note: **2 bytes shorter than applet AIDs**, no instance byte):

| Applet | Applet AID | Package AID |
|---|---|---|
| Teapot | `B00B5111CA01` | `B00B5111CA` |
| MemoryCard | `B00B5111CB01` | `B00B5111CB` |
| SingleUseKey | `B00B5111CD01` | `B00B5111CD` |
| BlindOracle | `B00B5111CE01` | `B00B5111CE` |
| SecureApplet (base) | `B00B5111FF01` | `B00B5111FF` |

`make install APPLET=memorycard` / `make uninstall APPLET=memorycard` wrap these
steps via `gp_helper.py` (which also refuses known-blacklisted keys).

## Per-applet quirks on J3R180

- **Teapot** — no PIN, no secure channel; ≤255 B payload. Fastest smoke test
  after install (`select` ≈ 61 ms).
- **MemoryCard** — secure-channel storage; a single secure-message payload is
  capped at 222 B total → **220 B of usable data** (fits any 24-word BIP39
  mnemonic). All commands except a few are PIN-protected.
- **SingleUseKey** — the one-time key **rotates on every `generate` and every
  `sign`**; fetching the pubkey twice without regenerating is the documented
  usage pattern (regression-tested in `test_singleusekey.py`).
- **BlindOracle** — BIP-32 derivation/signing; PBKDF2/seed-import paths trigger
  the deferred HMAC-SHA512 allocation (first such call in a session is slower).
- All SecureApplet subclasses: first command after install/power-up performs
  the deferred crypto initialization (see table above).

## Known limitations / open items

- J3H145 install failure (#3) — fix staged in PR #4 rebased branch
  `pr4-rebase-j3h145`; needs owner hardware verification.
- `CLEAR_ON_DESELECT` / `CLEAR_ON_RESET` pool sizes are not published by NXP
  for this part; estimates in issue #1 were derived behaviorally. Build with
  `DEBUG_BUILD=true` and use the `A0 00` diagnostic to measure on-card.
- Card #1 was externally factory-reset between 2026-03-20 and 2026-03-21
  (applets wiped, keys reverted to transport) — see `AGENTS.md` before reuse.
